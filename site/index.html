server companion + Flutter client for the pi coding agent

pi runs on your host.
You drive it from the sofa.

One Go process orchestrates a pi --mode rpc child per session and exposes REST /api/v1 plus WebSocket /ws/v1. The Flutter client streams the conversation, answers tool approvals, browses files, runs git and opens real PTYs — on Android, Linux and Windows. Provider keys and tokens stay on the server; the client only ever sees what it is allowed to see.

What it adds to pi

Everything pi does, from anywhere — plus what pi does not have

pi stays pi: the server forwards pi.* payloads verbatim and a new pi command needs no server change. What pi-ui adds are the surfaces a phone needs, each confined to the workspaces the operator allows.

One child per session

A supervisor spawns pi --mode rpc per session on the host, watches it, respawns it with resume after a crash and evicts what nobody is using.

Streaming chat

Assistant deltas, a collapsible thinking block, tool cards with their output and diff, and a replay that fills the gap after the socket dropped.

Approvals in your pocket

The bridge asks notify/confirm with a TTL; the card shows the command and denies on its own when nobody answers before it expires.

Steer or queue a follow-up

Send into the running turn, or leave a message the server delivers when the current tool calls finish. Attachments and slash commands pass through.

Files, git and search

Browse and read inside the roots, see status/diff/log and commit when git.write is on, search with ripgrep or across the session JSONL.

Terminals and tasks

Real PTYs over the WebSocket (terminal.open|input|resize|close) and background tasks in their own process group, stop included.

MCP and goal mode

The bridge configures MCP servers and registers their tools inside the session, and /goal keeps a long run pointed at one outcome.

Safe by construction

Device tokens are argon2id hashes, scopes bound what a client can do, revocation closes its sockets, TLS is pin-able, and --isolate puts a session in a container instead of your whole host.

How it is put together

A server that owns the sessions, a client that owns nothing

The server is the only process that holds a provider key, a device token hash or a session. The client is a remote control: it asks, streams and renders.

Clients
Flutter · Android 15+ Flutter · Linux Flutter · Windows one device token per device, kept in the OS keystore

↑ HTTPS · WSS — scopes are checked on every request and every frame ↓

Server (Go)
api · REST /api/v1 ws · hub, ring, since replay auth · pairing, scopes, revocation rpc · LF-only framing, backpressure sessions · spawn, watchdog, respawn with resume, eviction fs · git · search terminal · tasks · mcp · updates · settings store · SQLite (devices, cursors, audit) obs · audit and logs without conversation content

⇅ JSONL over stdio, split on \n only — stdout is the protocol, stderr is diagnostics

One child per session
pi --mode rpc pi-ui-bridge · approvals, MCP tools, goal mode conversation lives in pi's session JSONL
Host
your working directory git and ripgrep PTYs and background tasks optional: --isolate <image>, paths mounted same-path

The seam that keeps this expandable: new pi commands and events flow through the generic passthrough (POST /sessions/{id}/commands, WS session.command.raw) instead of a new server-side special case, and unknown fields are tolerated rather than rejected.

Run it

From a clone to a phone in the same room

Go 1.27+ to build the server; Node 22.19+ wherever the sessions run, because pi is a Node CLI.

cd server
CGO_ENABLED=0 go build -o bin/pi-ui ./cmd/pi-ui

./bin/pi-ui serve --addr 127.0.0.1:8787 --pi pi \
  --session /path/to/project[:name] \
  --bridge ../bridge/pi-ui-bridge.ts

serve starts one child per --session, serves REST and WebSockets, and on SIGINT/SIGTERM stops every terminal and task before reaping the children. --root <path> (repeatable) is what a client may browse, --session-dirs is what the message search reads, --state-dir holds the settings and the device tokens. Every flag also has a PIUI_* variable. 

./bin/pi-ui auth set-password           # the admin credential and the recovery path
./bin/pi-ui pair --url http://<host>:8787   # code, deep link and a scannable QR
./bin/pi-ui status                      # devices, password, pending invitations
./bin/pi-ui tls fingerprint --cert cert.pem   # what the app compares when it pins

An invitation is single-use and expires after ten minutes; the app burns it and keeps the device token in the OS keystore. deploy/ carries the container that mounts the projects same-path, and the systemd unit for the static binary. 

cd server
gofmt -l . && go vet ./... && go test -race ./... && CGO_ENABLED=0 go build ./...

server/scripts/measure.sh   # spawn latency, RSS, WS throughput, the three-minute soak

The suites need neither a model nor a network: server/test/fake-pi impersonates pi --mode rpc deterministically, test/e2e drives the built binary, and test/adversarial attacks the framing, the WebSocket and the REST surface.

Security

What this deployment trusts, and what it never reveals

Every row below is a rule with a test next to it, not an intention: docs/security.md is written so that each sentence can point at the code that enforces it.

LayerRule
Network--allow-ips refuses a peer outside the list with 403 forbidden_scope before any handler runs, and audits the refusal.
Transport--tls-cert/--tls-key terminate TLS 1.2+; GET /server reports the leaf's SHA-256, which the app pins when it pairs.
IdentityA device token is <deviceId>.<secret>: O(1) on the id, constant-time on the hash. Revoking a device closes its sockets immediately.
Scopeviewer reads · operator drives sessions and the host · admin manages the server itself. Every request and frame is authorized against the stored scope.
PathEvery host path is resolved — symlinks included — and confined to a --root; outside is path_escape, audited.
ProcessA terminal or a task gets its own process group and is signalled as a group, so no child outlives it.
ContentLogs never carry tokens or conversation content, and the client only ever receives a nickname for a provider.

Pairing

  1. pi-ui pair mints a six-character Crockford base32 code: ten minutes of TTL, single use, five attempts per minute per IP.
  2. The server prints the card itself on first start — origin, code, piui://pair link and QR — and the app types, pastes or scans the same invitation.
  3. POST /auth/pair burns it and returns the token exactly once; on a self-signed certificate the app confirms the fingerprint, which the link already carries.
  4. The token goes to the keystore, the profile to plain preferences; a refresh rotates the secret and keeps the device id.

What a leaked token can do

  • viewer: read sessions, files, git state and search results — nothing else.
  • operator: the above plus prompting, steering, aborting, tasks, PTYs, writes inside the roots and git writes when git.write is on.
  • admin: all of that plus the server's own policy — and still no provider key, because none is stored in a form a client can fetch.

Deliberately not defended

  • A hostile host: the server runs with the operator's privileges — that is what --isolate <image> bounds.
  • Traffic analysis on plain HTTP: on a network you do not trust, terminate TLS or sit behind a VPN.
  • A hostile pi or provider: a malformed line becomes pi.unknown, never an instruction to the server.

Roadmap

Eight phases, and the gaps named instead of hidden

The phases are documented to be resumable, each with its exit criterion: docs/roadmap.md.

  • ✓
    Phase 0 — DefinitionADRs 0001–0009, the protocol documents, schemas/ as the source of truth, the generated Go types drift-checked in CI.
  • ✓
    Phase 1 — Server spike (Go)LF-only framing, backpressure, WebSocket fan-out with since replay and the fake-pi harness; the measured criteria held, so no fallback was needed.
  • ✓
    Phase 2 — Mockup42 screens for phone and desktop, and the tokens the app reads: mockups/assets/styles.css → app/lib/core/theme/theme_tokens.dart.
  • ✓
    Phase 3 — Server coreAuth, REST and WS, the session supervisor with respawn and eviction, audit, health, rate limits, drain.
  • ✓
    Phase 4 — App corePairing with the keystore, the session list, streaming chat with replay and reconnection, approvals, notifications, the three targets.
  • ✓
    Phase 5 — Server parityFiles, git, search, terminals, tasks, settings, MCP, updates, goal mode and drain — with session.command.raw carrying every other pi command untouched.
  • ✓
    Phase 6 — App parityThe full set of screens, catalogue-driven settings, themes, and the client's own translations (app_en.arb → app_it.arb).
  • ~
    Phase 7 — Security and networksDelivered: TLS with a pinned fingerprint, the audited peer allowlist, scopes and revocation, path confinement, rate limits and container-per-session isolation. Named boundary: a containerised server cannot spawn session containers that mount host paths, so deploy/ ships without --isolate and says why.
  • ✓
    Phase 8 — DistributionTag → binaries, bundles, checksums and a GitHub release; Docker image and Compose reference, hardened systemd unit, the Arch PKGBUILD and the Inno Setup script. Missing by name: AppImage and proper code signing.
